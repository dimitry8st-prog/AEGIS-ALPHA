# Проверка AEGIS-ALPHA — 03.10.2026

Исходный commit: `524ba7098b36958842f00ec02573c87b78af7563`.

## Вывод

Это основа API и инфраструктуры с черновиками исследовательского сбора данных. По текущему коду нельзя считать систему готовой к сбору, анализу или выдаче торговых сигналов. Docker запускает `app.main:app`; `src/main.py` не является используемой точкой входа. Связь проекта с обсуждавшейся страницей «Долголетие» по содержимому репозитория не установлена.

## Подтверждённые проблемы

| Приоритет | Место и наблюдение | Следствие и исправление |
|---|---|---|
| Высокий | `src/config/settings.py` отсутствует; `src/main.py` использует абсолютные импорты, сборщики — относительные; зависимости Telethon, yfinance, pandas, numpy отсутствуют в requirements | Черновики не запускаются из текущего образа. Выделить пакет worker с едиными импортами, конфигурацией и зависимостями |
| Высокий | `init.sql` и SQL в `src/main.py` задают разные `users` и `audit_logs`, включая UUID против VARCHAR и разные поля | Нельзя безопасно объединить через CREATE TABLE IF NOT EXISTS. Нужны миграции и отдельное имя/схема аудита сборщиков |
| Высокий | `TelegramCollector.save_message` и `MarketDataCollector.save_market_data` перехватывают ошибки записи без возврата отказа; `_collect_and_save` возвращает True после такой записи | Счётчик успеха может объявить несохранённые данные успешными. Возвращать подтверждённый результат и учитывать FAILED_RECORD |
| Высокий | `/results` в `app/main.py` вставляет title и description в HTML без экранирования; у маршрута нет зависимости проверки авторизации | Возможны stored XSS и просмотр items без входа. Экранировать текст шаблонизатором/escape, определить и проверить политику доступа |
| Средний | Docker HEALTHCHECK импортирует requests, которой нет в requirements, и не проверяет HTTP статус | Проверка может падать при живом API; даже HTTP ошибка не даёт правильный сигнал. Использовать urllib из стандартной библиотеки с timeout и проверкой ответа |
| Средний | `/health` в `app/main.py` всегда возвращает healthy, не проверяя PostgreSQL/Redis | Это liveness, не readiness. Добавить отдельный readiness endpoint с реальными проверками зависимостей |
| Средний | `collect_ticker_data` возвращает Dict при загрузке и DataFrame при попадании в Redis; `_collect_and_save` ожидает truthiness и Dict | Повторный сбор из кэша может завершиться ошибкой. Выбрать единый контракт результата; тестировать hit/miss |
| Средний | Ключ записи котировок основан на collected_at; это время нового сбора | Повтор одного периода может создать новую запись. Использовать timestamp котировки и ключ provider/symbol/interval/time/adjustment |
| Средний | В `.gitlab-ci.yml` вызывается pytest tests/ --cov=src, но tests/ нет, pytest и pytest-cov не включены в requirements | CI описан для GitLab, но не готов к запуску; для GitHub workflow отсутствует. Добавить dev dependencies и реальные тесты app/worker |

Compose также содержит локальные пароли по умолчанию и открытые порты PostgreSQL/Redis/Grafana. Для внешнего размещения понадобятся отдельные секреты, ограничения сетевого доступа и настройки CORS. Наличие компрометации не установлено; проверка зависимостей на известные уязвимости не выполнялась.

## Варианты реализации

1. **Гибрид n8n + Python worker + PostgreSQL:** n8n запускает пакет и показывает статусы; worker принимает параметры, работает с источниками и БД, возвращает результат. n8n в текущем compose отсутствует, его нужно добавить отдельно. Удобный вариант для учебного MVP.
2. **Python worker в существующем проекте:** сохранить API `app/`, вынести адаптеры `src/` в отдельный пакет/контейнер с расписанием и устойчивыми состояниями в PostgreSQL. Меньше новых инструментов, больше собственного кода; подходит для дальнейшего развития.
3. **Ручной исследовательский пакет:** разрешённые экспорты новостей и котировок, Python/CSV, контроль качества. Подходит для проверки гипотезы до постоянного сбора.

Для начала рекомендован вариант 1, если нужен визуальный сценарий урока; вариант 2 — если главным результатом будет поддерживаемый программный сервис. Не подключать оба существующих SQL-контура к одной БД без миграций.

## План интеграции BPMN

- Сохранить работающую точку входа API. Создать отдельный worker и контракты Collect / Record / IO из [описания процесса](aegis-alpha-bpmn.md).
- Через миграции добавить news, quotes, collection_runs, manifests, quarantine, source_cursors; задать уникальные ключи, транзакции и историю версий.
- Начать с ручного пакета по одному разрешённому источнику каждого типа. Реализовать ограниченные повторы, проверку неизвестного исхода записи и дедлайн.
- Проверить дубли, невалидные записи, отказ одного источника, отказ БД и повтор пакета. После этого включить расписание.
- Аналитику и сигналы вынести в следующий процесс после накопления проверенного датасета.

## Что проверено и что добавлено

Проведён статический просмотр точки входа, Docker/compose, SQL, CI и черновиков. `python -m compileall -q app src` проходит: это проверка синтаксиса, не импортов и не работоспособности. Docker в среде проверки отсутствует; контейнеры, внешние источники и интеграционные тесты не запускались.

Добавлены описание для домашнего задания, четыре связанные диаграммы в PNG/SVG, BPMN 2.0 XML и генератор. Runtime и существующая БД не изменены. XML помечен isExecutable=false: это модель для реализации, а не готовый workflow n8n.

Для сдачи задания разместите основной PNG и при необходимости схемы подпроцессов в Miro или Яндекс.Досках, приложите скриншот доски и описание границ/условий. Доска в этой сессии не создавалась.
